# 요청·문서·복구 안정화 — 2.0 preview

이번 버전은 **호출 계약이 변경된 시험판**이다. 기존 클라이언트가 변경 도구에 요청 ID와 문서 문맥을 보내지 않으면 실행을 거절한다. 먼저 별도 시험 모델에서 검증하고 사용한다. 컴파일·독립 로직 검사 결과는 [VALIDATION.md](VALIDATION.md)에 있으며, 실제 Revit 이벤트·작업 결과·속도는 아직 측정하지 않았다.

## 변경 요청 순서

1. `get_document_context`를 호출한다. 반환값 `active.expectedDocument`, `active.expectedRevision`을 보관한다.
2. 변경 도구에 두 값과 고유한 `requestId`를 보낸다. 새 해석·간섭 뷰·CAD 적용 도구는 기본값이 `dryRun: true`이다. 미리보기도 세 보호 인자를 요구한다.
3. 미리보기 결과를 검토하고 최신 문맥으로 `dryRun: false`를 실행한다. 미리보기와 실제 적용은 인자가 다르므로 **서로 다른 요청 ID**를 사용한다.
4. 연결 끊김·시간초과가 나면 원래 ID로 `get_request_status`를 조회한다. 같은 작업을 재전송할 경우 ID와 작업 인자를 그대로 유지한다. 결과가 불명확할 때 새 ID를 발급하여 반복하지 않는다.

```json
{
  "requestId": "energy-change-001",
  "expectedDocument": "<active.expectedDocument>",
  "expectedRevision": 0,
  "patch": {"includeThermalProperties": true},
  "dryRun": true
}
```

위 예시는 `update_energy_settings` 인자다. 결과의 `_meta.status`가 `succeeded`인지 확인한다. 이는 도구 호출이 끝났다는 뜻이다. 개별 도구의 `dryRun`, `notApplied`, 누락·오류·완료 여부도 별도로 확인해야 한다. HTTP 200이나 `isError: false`만으로 모델 변경 완료를 판단하지 않는다.

## 문서 보호

토큰은 Revit 세션과 문서 객체에 귀속된다. 제목이 같은 다른 문서, 활성 문서 전환, 세션 재시작을 구분한다. 요청이 실제 실행되기 직전에 활성 문서와 수정번호를 검사하며, 문서를 자동으로 전환하지 않는다. Revit의 `DocumentChanged` 이벤트가 전달되면 수정번호를 증가시킨다. 문서가 바뀌었다면 새 문맥과 계획을 검토한 뒤 새 요청을 만든다.

이 보호는 모델 전체의 잠금이나 내용 해시가 아니다. 선택·활성 뷰·외부 링크 파일·외부 파일 변경을 모두 추적하지 않는다. 필요한 도구는 별도 파일·뷰 검사를 한다. `send_code_to_revit`과 `use_module`은 항상 변경 도구로 취급하지만, 임의 C# 코드가 다른 문서나 파일을 직접 건드리는 것을 차단하는 샌드박스는 아니다.

## 상태·시간초과·서버 중지

| 상태 | 의미와 후속 동작 |
|---|---|
| `queued` | 아직 실행 전. `cancel_request`로 취소 가능 |
| `running` | 실행 중. 같은 ID로 상태 조회; 강제 중단하지 않음 |
| `succeeded` | 호출 결과 저장됨. 도구별 결과도 확인 |
| `failed` | 예외 발생. 임의 코드·외부 해석 등의 부분 결과가 남을 수 있음 |
| `cancelled_before_execution` | 실행 전 취소됨. 취소한 ID는 재실행하지 않음 |
| `failed_before_execution` | 시작 상태를 기록하지 못해 실행하지 않음 |
| `unknown_after_restart` | 이전 세션/다른 프로세스의 완료를 확인할 수 없음. 모델·파일을 조사하고 자동 재실행 금지 |
| `completion_not_persisted` | 실행은 끝났으나 최종 결과 저장 실패. 자동 재실행 금지 |
| `not_found` | 이 저장소에서 ID를 찾지 못함. 다른 서버·저장소인지 확인; 미실행의 증거는 아님 |

시간초과 전에 시작하지 않은 작업은 취소한다. 이미 시작한 Revit API·C# 코드는 계속 실행될 수 있고 상태 조회로 완료를 확인한다. MCP의 일반 취소 알림만으로 실행 중인 모델 작업을 강제로 멈추지 않는다. 시스템 해석은 별도 `cancel_systems_analysis` 도구를 사용한다.

리본에서 서버를 중지하면 새 요청을 막고 대기 작업을 취소한다. 이전 연결은 재시작 후 새 요청을 넣을 수 없다. 이미 실행 중인 작업을 되돌리는 버튼은 아니다. 서버 재시작 뒤에는 새 연결을 사용한다.

## 중복과 기록

변경 요청은 실행 전에 `RevitMcpData/requests`에 기록한다. 같은 ID·같은 인자는 기존 결과를 반환하며, 같은 ID·다른 인자는 거절한다. 지문은 속성 순서를 정규화하고 대기 시간과 요청 ID를 제외한 인자 전체를 포함한다. 문맥·`dryRun` 변경도 다른 작업으로 간주한다.

초기 기록 생성은 배타적인 파일 이동으로 처리하므로 같은 기록 폴더를 사용하는 독립 큐가 동시에 같은 ID를 받아도 한 큐만 실행한다. 기존 기록은 임시 파일과 원자적 교체로 저장한다. 기록이 손상되거나 쓰기에 실패하면 변경 요청을 실행하지 않는다. 시작/대기 상태로 남은 기록은 재시작 후 불명확한 결과로 반환한다.

이 보장은 기록 폴더를 보존하고 같은 ID를 사용하는 범위에 한정된다. 새 ID, 다른 저장소, 기록 삭제·수정으로 중복 방지를 우회할 수 있다. 일반 읽기 요청의 기록은 메모리 한정이다. 로컬 데이터 도구는 별도 JSON 저장소를 사용하며 Revit 요청 기록 대상이 아니다. 기록에는 인자 지문과 결과가 남으므로 업무 데이터와 함께 관리한다. 자동 기록 삭제 기능은 아직 없다.

로컬 컬렉션 JSON의 읽기-수정-쓰기는 **같은 프로세스 안에서만** 직렬화한다. 여러 Revit 프로세스에서 같은 컬렉션을 동시에 수정하는 운용은 지원하지 않는다. 이는 요청 기록의 배타적 선점 보장과 별개이다.

## 실패 복구와 응답성

공통 트랜잭션은 Revit 오류를 롤백하고 커밋 상태를 확인한다. CAD 일괄 적용·간섭 뷰 생성은 한 트랜잭션으로 처리한다. 시스템 해석 보고서 생성/백그라운드 요청 및 임의 C#의 수동 트랜잭션·파일 쓰기는 전체 원자성을 보장하지 않는다. 실패 결과에 남은 보고서 ID·경로를 확인한다. 도구는 모델 저장·동기화를 자동 수행하지 않는다.

대기열은 64개, HTTP 연결은 32개, 요청 본문은 8 MiB로 제한한다. Revit 이벤트 한 번에 최대 4개 작업을 시작하고 작업 사이에 경과 시간을 검사한다. 단일 무거운 API 호출을 100 ms 안에 끊는 기능은 아니다. 모델 작업을 여러 스레드에서 동시에 실행하지 않는다. 간섭 검사에는 후보·기하 계산 한도가 있고 한계·누락을 보고한다. CAD는 최대 100개 배치를 한 번에 적용한다.

이러한 장치는 중복 실행과 잘못된 대상 변경을 줄이기 위한 것이다. 기존 버전이나 다른 MCP보다 빠르다는 실측 결과는 아직 없다. 별도 시험 모델에서 중복 요청, 문서 전환, 시간초과, 서버 중지/재시작, CAD 좌표, 간섭 결과와 해석 결과를 확인해야 한다.
